# C++ 代码规范

## 适用范围

本文规定项目自有C++代码的命名、排版、注释、头文件、接口及测试组织。
第三方代码（包括common/softfloat）保留上游风格，不参与全仓格式化。
目录职责见根目录AGENTS.md，测试运行与日志见[验证规范](../verification.md)。

## 自动排版

根目录`.clang-format`为排版的唯一机器可读定义，固定使用clang-format **18.1.8**，
`.editorconfig`提供编辑器的UTF-8、LF和空格缩进设置。可在开发用虚拟环境中
安装`python -m pip install clang-format==18.1.8`。规则包括：

- 缩进4空格，禁用制表符；目标行宽100，长注释和不可拆字符串可例外。
- 左大括号跟随声明或控制语句，类访问标签与class对齐，namespace不增加缩进。
- 独立语句独立占行，函数体、if/for/while均展开；控制分支使用大括号。
- 长参数列表换行，不挤压多个参数；同一include组按工具规则排序，保留分组。
- 保留中文注释内容，工具不重新折行注释；每个成员单独声明并保留用途说明。

日常先编辑，再使用`python3 scripts/format_cpp.py --write`；工具不在PATH时传
`--clang-format /绝对路径/clang-format`。脚本统一枚举hw/include、hw/model、
hw/verif、sw/driver的.h/.cpp，排除SoftFloat，不受工作区是否已提交影响。
配置测试时通过`-DHELO_CLANG_FORMAT=/绝对路径/clang-format`指定工具；
`cmake --build <构建目录> --target format-check`或CTest的`cpp_style_test`
只检查不改文件，并按仓库要求保存日志。版本不匹配或排版漂移会失败。
仅构建模型库（BUILD_TESTING=OFF）不要求安装格式化工具。

## 接口与测试组织

- 多项资源参数采用具名配置记录；GpuConfig持有ShaderConfig，ShaderConfig持有ExecutionConfig。
- 公共运行结果按状态枚举判断，文字诊断只供阅读；底层参数异常可由执行边界转换为结构化故障。
- 共用功能测试按模块依赖GeomDut/RastDut/TexDut/RopDut，避免一个接口承担全部图形模块。
- C++游标、句柄和分配生命周期的检查放在`tests/func/`，不要求RTL提供软件实现细节。
- 测试按准备输入、执行、断言组织；重复场景提取有名称的辅助函数，期望值独立于生产算法。
- 函数职责概述保留，复杂实现补充约束、失败提交边界和资源寿命，不用注释复述每一行赋值。

## 命名规则

| 类别 | 规则 | 示例 |
| --- | --- | --- |
| 类型 | 使用 `CamelCase`，适用于 `class`、`struct`、`enum`、`using` 或 `typedef` 定义的类型 | `FileReader`、`TaskState`、`ColorMode` |
| 函数 | 使用 `snake_case`，适用于普通函数、成员函数和静态函数 | `load_config()`、`parse_header()`、`create_buffer()` |
| 普通变量 | 使用 `snake_case`，适用于局部变量、函数参数和普通命名对象 | `file_path`、`retry_count`、`current_size` |
| 成员变量 | 使用 `m_` 前缀加 `snake_case` | `m_buffer`、`m_current_index`、`m_retry_count` |
| 常量 | 优先使用 `UPPER_SNAKE_CASE`，适用于 `constexpr`、枚举常量和具有稳定常量语义的命名对象 | `DEFAULT_TIMEOUT`、`MAX_CONNECTIONS`、`PI_VALUE` |
| 宏 | 使用 `UPPER_SNAKE_CASE` | `ENABLE_LOGGING`、`DEFAULT_PORT`、`BUILD_WITH_SIMD` |
| 文件 | 使用小写，需要分词时使用 `snake_case`；扩展名沿用仓库现有选择，不强制使用 `.h` 或 `.hpp` | `file_reader.h`、`task_queue.cpp`、`string_utils.hpp` |
| 命名空间 | 使用小写，需要分词时可使用下划线 | `core`、`image_io`、`network_utils` |
| 模板类型参数 | 使用 `CamelCase`；简单场景可使用单字母，通常优先使用有语义的名称 | `T`、`KeyType`、`ValueType` |

仅带有 `const` 修饰、但语义上仍是普通变量的局部对象或成员对象，可继续使用普通变量或成员变量的命名规则。

## 风格一致性

- 新模块采用本文约定；已有模块保持内部风格一致。
- 功能修改和缺陷修复不混入无关的标识符、文件或接口重命名。
- 风格统一作为独立变更提交，便于审查和追踪。

## 注释

- 注释使用中文；已有模块采用其他语言时，保持该模块的注释语言一致。
- 注释应准确、简洁，与代码行为保持一致；修改相关逻辑时，应同步更新注释。

### 类、成员变量与函数注释

- **统一要求**：每个 `class` 定义、每个类成员变量及每个函数定义均须附有一句完整、简洁的注释，分别说明类的主要职责、成员变量的用途或含义、函数的主要行为；不得仅复述名称或逐项描述实现步骤。
- **覆盖范围**：类包括模板类、嵌套类及局部类；成员变量包括静态和非静态成员，不论访问权限；函数包括普通函数、成员函数、构造函数、析构函数、运算符重载、模板函数和测试函数，内联函数及短函数同样适用。
- **放置位置**：类和函数的注释紧邻定义，位于模板声明、属性说明或定义签名之前；前置声明或函数声明处的注释不能替代定义处的职责概述。成员变量的注释紧邻类内声明，可放在声明上一行或行尾；每个成员变量均须有明确对应的说明。
- **注释形式**：可使用 `//` 注释或文档注释，已有符合要求的概述时不重复添加。
- **补充说明**：存在关键约束、单位、取值范围、前置条件、输入输出约束、状态修改、副作用或线程安全要求时，应在概述后补充说明。

示例：

```cpp
// 保存计数状态并提供递增操作。
class Counter {
public:
    // 将计数值增加一。
    void increment() {
        ++m_value;
    }

private:
    int m_value = 0; // 记录当前累计次数。
};
```

### 实现注释

- 复杂分支、边界条件、非直观算法以及性能、资源生命周期或线程安全约束，应在相关代码附近说明。
- 实现注释应解释设计原因或使用限制，避免重复代码已明确表达的操作。

## 代码组织

- 按功能聚类组织代码。新增逻辑优先放到语义最接近的位置，并尽量复用已有实现，避免相近能力分散或重复。
- `.cpp` 文件中的实现顺序尽可能与对应头文件中的声明顺序一致。如因依赖关系、局部辅助函数或平台分支需要调整，可在局部合理偏离。
- 非模板、非 `inline` 的函数声明通常放在头文件中，实现放在源文件中；模板、必须内联的短实现，以及确实需要头文件可见的实现除外。

## 头文件与命名空间

- 保持 `#include` 简洁，只包含必要头文件；已由直接包含的头文件间接引入的头文件不重复包含。
- 在头文件中不使用 `using namespace`，也不在公共头文件中通过 `using` 暴露外部命名空间中的类型或符号。
- 涉及 `std` 等命名空间时，头文件中优先使用全限定名，例如 `std::string`、`std::vector`。
- 在源文件或局部作用域中，如明显提升可读性，可谨慎使用有限范围的别名或 `using` 声明。
